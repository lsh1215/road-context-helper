# 초행길 — 제품·개발 계획서

작성일: 2026-11-14 (한국 시간) / 상태: 공모전 MVP 개발 인계용 v1

실행 기준 추가: [성공 기준 기반 개발 실행 계획](./road-context-helper-execution-plan.md). 구현 순서·성공 게이트·반복 검증·작업 경로는 이 실행 계획을 따른다.

## 1. 제품의 목적

**처음 가는 복잡한 도로에서도, 그 길을 자주 다니는 사람처럼 ‘앞으로 차로가 어떻게 이어지는지’를 미리 이해하도록 돕는 차량용 안내 앱.** 내비게이션의 방향 안내를 도로 구조 설명으로 보완한다.

사용자가 강조한 문제는 ‘오른쪽으로 3개 차로를 옮겨야 한다’가 아니다. 최종 정정된 핵심 사례는 **진입 직후 서둘러 옆 차로로 옮기려 하지 않아도, 진입한 차로가 일정 구간 이어지고 끝에서 차로가 줄어들며 합류하는 구조를 초행 운전자가 미리 알기 어렵다**는 것이다.

사용자가 기억하는 이동은 용산역→월곡역 방향, 내부순환로로 갈아타던 곳이다. 정확한 램프·도로·차로는 아직 특정하지 못했다. 이 설명을 근거로 특정 IC를 확정하거나 해당 구간에 그런 구조가 실제로 있다고 단정하지 않는다.

제품이 답할 질문은 세 가지다.

1. 내가 진입할 도로는 어떤 형태로 이어지는가?
2. 진입 차로가 바로 끝나는가, 일정 구간 이어진 뒤 합류하는가?
3. 그 구조를 이해하기 위해 지금 미리 알아두면 좋은 정보는 무엇인가?

‘차량 사이에 지금 들어가도 되는가’, ‘누가 먼저 양보해야 하는가’, ‘어느 차로가 더 빠른가’는 MVP가 답하지 않는다. 핵심 효용은 불필요하게 이른 차로 변경 시도와 구조를 뒤늦게 이해하는 당황을 줄이는 것이다. 실제 감소 효과는 사용자 테스트 전까지 가설이다.

## 2. 사용자와 사용 환경

| 사용자 | 구체 상황 | 원하는 결과 |
|---|---|---|
| 운전은 가능하지만 해당 길이 처음인 사람 | 합류 후 차로 끝이 안 보여 바로 옆으로 옮기려 한다 | 합류 형태와 차로 지속 구간을 사전에 이해 |
| 초보·운전 재개자 | 차로가 줄어드는 구간에서 방향 안내만 듣고 불안해한다 | 짧고 일관된 구조 안내 |
| 여행·출장 운전자 | 낯선 도시의 램프와 복잡한 분기점을 통과한다 | 도로를 지나기 전에 간단한 예습 |

주 사용 시점은 복잡한 구간에 도달하기 전이다. 이미 합류 끝에 도달했을 때 긴 설명을 읽게 하는 제품이 아니다. 지역 전문 운전자와 교통 정체 우회가 주목적인 운전자는 첫 대상에서 제외한다.

## 3. 기존 내비와의 관계·차량 앱의 이유

내장 내비는 목적지와 경로 안내를 담당하고, 이 앱은 검증된 특이 구간의 차로 연결 구조를 설명한다. 경로 계산·턴바이턴 전체 기능을 새로 만들지 않는다. 기존 업체가 같은 기능을 전혀 제공하지 않는다고 주장하지 않는다. 이 문서는 경쟁사 기능 부재를 검증한 자료가 아니다.

차량 앱의 이점은 실제 내장 내비의 경로 식별·안내 이벤트와 위치를 받아 필요한 시점에 설명하고, 차내 화면과 음성을 통해 조작 없이 전달하는 데 있다. 스마트폰에서도 유사 기능을 만들 수 있지만, 차량에 연결된 안내 흐름과 통합하는 것이 제품 방향이다. 미확인 센서·ADAS·카메라 데이터를 차별점으로 내세우지 않는다.

## 4. 제품 계약: 어떤 말을 할 수 있는가

### 기본 제공 문구: 도로 구조의 사실

> “앞 진입로는 합류 지점까지 차로가 이어집니다.”
> “진입 차로는 끝부분에서 왼쪽 차로와 합쳐집니다.”

위 문구도 해당 구조가 검증된 구간에서만 사용한다. 왼쪽·오른쪽은 진행 방향을 기준으로 작성한다.

### 현재 차로를 모를 때

> “진입로 차로에 있다면, 앞 합류 지점까지 이어지는 구조입니다.”

조건부 표현과 도로 전체 도식을 사용한다. 내 차가 어느 차로인지 아는 것처럼 도식에 자동차 아이콘을 꽂지 않는다. 일반 GPS와 NaviHelper의 `currentRouteIndex`로 차로를 확정할 수 없다.

### 제공하지 않는 문구

- “지금 차로 변경하지 마세요.”
- “끝까지 가서 끼어드세요.”
- “지금 합류해도 안전합니다.”
- “앞까지 가면 더 빨리 갈 수 있습니다.”

이는 단순 면책 문구 문제가 아니라 데이터 범위의 한계다. 주변 차량·공사·실선·차로 통제·운전자 현재 차로를 확인하지 않은 상태에서 행동을 단정하면 앱의 설명을 잘못 적용할 수 있다. 실제 안내는 현장 표지·노면 표시와 주변 교통을 대신하지 않는다.

## 5. MVP 범위

| 우선순위 | 기능 | 구현 범위 |
|---|---|---|
| P0 | 검증된 특이 구간 카탈로그 | 1~3개 구간; 출처·방향·검증일 필수 |
| P0 | 경로·위치 기반 구간 접근 판정 | 도로 corridor, 진행 방향, 경로 세션 확인 |
| P0 | 차로 연결 구조 사전 안내 | 하나의 도식과 1~2문장 |
| P0 | 단계별 노출과 반복 억제 | 예고→접근→통과; 상황에 따라 생략 |
| P0 | 데이터 부족 시 안내 중지 | 위치·도로·방향 불명확 시 행동성 안내 없음 |
| P0 | 실제 SDK/시연 입력 분리 | 동일 엔진을 쓰되 출처를 항상 보존 |
| P0 | 재경로·오래된 지도·앱 수명 처리 | 이전 경로의 안내가 남지 않음 |
| P1 | 음성 안내 | 실제 포커스·내비 음성 중복 검증 후 활성화 |
| P1 | 출발 전 구간 예습 | 정차 상태 또는 시연 전용 |
| P1 | 잘못된 구조 신고 | 정차 후 간단 기록; 주행 중 입력 금지 |
| P2 | 지역 확대·자동 후보 추출 | 지도 데이터 품질·운영 절차 확보 후 |

MVP는 검증된 한 유형, 즉 ‘진입 차로가 이어지다가 끝에서 합류하는 구간’에 집중한다. 연속 진출·다차로 이동 안내는 별도 확장이다. 차선 변경 제어, 자동운전, 차량 간 합류 순서 판단, 실시간 빈틈 탐지, 정체 추월 전략, 전국 자동 서비스는 범위 밖이다.

## 6. 실제 SDK 테스트 결과: 반드시 인계할 사실

환경: Pleos Connect 2.1.0 arm64/API 34, Emulator 37.2.13, NaviHelper 3.0.5. 기존 테스트 앱은 `dev.pleos.naviprobe`다.

| 항목 | 관측 결과 | 해석의 한계 |
|---|---|---|
| NaviHelper 연결 | 성공 | 실제 차량 동작까지 검증한 것은 아님 |
| 위치 콜백 | 50건, 고유 좌표 1개 | 실제 이동 갱신 성공 아님 |
| TBT 콜백 | 빈 목록 17건, 10개 항목 목록 33건 | 항상 최대 10개라고 단정할 수 없음 |
| 진입·진출 동시 수신 | 같은 목록에서 확인 | 차로 구조·현재 차로 제공 증거 아님 |
| 요청 목적지 | 월곡역 부근 | 출발 위치가 용산역으로 반영되지 않음 |
| 실제 응답 출발 위치 | 성남 기본 좌표 37.4127212, 127.094681 | 사용자가 말한 경로의 재현 아님 |
| GPS 입력 | Android에는 용산역 좌표 반영 | 내비가 NMEA 체크섬 오류를 기록하며 위치는 정체 |

실제 한 목록에 들어온 일부 항목:

| 순서 | type | description | 원본 distance |
|---|---|---|---|
| 1 | TURN_ENTER_IC_R | 동부간선로 방면 | 8500 |
| 2 | TURN_ENTER_OVER_R | 내부순환로(성산) 방면 | 1200 |
| 3 | TURN_EXIT_IC_R | 월곡IC - 북부간선도로 방면 | 6100 |

위 표의 순서는 전체 목록 중 발췌한 상대 순서다. distance는 뒤 항목으로 갈수록 커지는 값이 아니었다. 현재 위치 기준 거리인지 구간 간 거리인지 실측 확인 없이 차감·누적해서 ‘합류 후 몇 m’라고 계산하지 않는다. 문자열에 ‘내부순환로’가 있다는 이유만으로 사용자 사례와 같은 구간이라고 판단하지 않는다.

## 7. 필요한 데이터와 확보 전략

| 데이터 | 사용 목적 | 현재 상태·확보 방식 |
|---|---|---|
| 위치·진행 방향·routeId | 현재 주행 맥락과 방향 | NaviHelper 필드 확인; 이동 갱신 미통과 |
| TBT type·description·distance | 경로 맥락 보조·진입 후보 식별 | 실제 목록 수신 확인; 거리 의미 추가 검증 |
| 진입 차로의 지속·종료 위치 | 핵심 구조 설명 | SDK 응답에서 확보 못 함; 외부 데이터 필요 |
| 차로 연결 관계·차선 종류 | 어디서 합류하는 구조인지 구분 | 외부 정밀도로지도 및 검수 필요 |
| 현재 차량의 차로 | 특정 차로 유지 지시 | 미확보; MVP는 이를 전제로 하지 않음 |
| 공사·통제·임시 차로 | 구조 데이터 무효화 | 자동 공급 미확보; 지원 범위 제한·운영 검수 |
| 주변 차량·합류 가능 간격 | 즉시 행동 판단 | 미확보; 제공하지 않는 기능 |

1차 후보는 국토지리정보원 정밀도로지도다. 차선 단위 도로 구조 자료를 제공하는 데이터원이지만, **선택 구간의 최신 수록 여부·스키마·차로 연결 표현·재배포 조건은 아직 확인하지 않았다.** 다운로드 가능하다는 사실과 원하는 topology가 바로 준비된다는 사실을 구별한다. [국토교통부 정밀도로지도 소개](https://www.molit.go.kr/USR/NEWS/m_35045/dtl.jsp?id=95086390&lcmspage=1), [국토정보플랫폼](https://map.ngii.go.kr/)

확보 절차:

1. 먼저 실제 시험 구간을 특정한다. 사용자 구간을 특정하지 못하면 다른 검증 가능한 구간을 선택하고 대체 구간임을 표시한다.
2. 구간의 방향별 도로 중심선·차로 연결·합류 끝점·규제선 자료를 확보한다. 도로/차로 ID, 좌표계, 제작일, 이용 조건을 기록한다.
3. 원본의 필드 이름을 확인한 뒤 앱 모델로 변환한다. 특정 파일명이나 필드가 존재한다고 가정해 importer를 작성하지 않는다.
4. 사용 가능한 최신 영상·지도·현장 자료로 구조를 교차 확인한다. 지도 화면을 무단으로 수집·배포하지 않는다. 출처와 검수자가 없는 실제 구간은 승인하지 않는다.
5. 자료가 불완전하면 실제 서비스 대상에서 제외한다. 도식을 직접 그릴 수는 있지만, 그 도식이 실제 구간의 사실이라는 증거가 생기는 것은 아니다.
6. 실제 자료 확보 전에는 이름 없는 가상 도로 fixture로 UI·엔진을 개발한다. 실제 장소명과 가상 구조를 결합하지 않는다.

일반 POI 데이터와 TBT 문자열만으로 차로 종료 지점을 생성하지 않는다. 다른 지도 서비스는 공식 API가 제공하는 필드·이용 조건을 확인한 뒤 대체 후보로 평가한다. LLM으로 실제 도로 구조를 추정해 자동 배포하지 않는다.

## 8. 화면과 정보 설계

### S1. 대기 화면

‘경로에서 복잡한 구간을 찾고 있어요’, SDK 연결 상태, 구조 데이터 지원 범위만 표시한다. 미지원 지역에서 ‘앞으로 복잡한 구간이 없습니다’라고 단정하지 않는다. 앱 시작 시 내비 목적지를 변경하지 않는다.

### S2. 구간 예고 카드

- 제목: ‘앞 진입로의 합류 구조’.
- 그림: 도로 진행 방향, 이어지는 진입 차로, 끝에서 합쳐지는 지점. 자동차의 현재 차로 아이콘은 없음.
- 한 줄: ‘진입 차로가 합류 지점까지 이어집니다’.
- 거리는 신뢰할 수 있게 계산됐을 때만 ‘약 400m 앞’처럼 표시한다. 검증되지 않았으면 거리 숫자를 생략한다.
- 카드 전체 읽기 목표는 3초 내. 주행 중 상세 지도·긴 설명·스크롤을 요구하지 않는다.

### S3. 구간 접근 상태

같은 설명을 크게 다시 띄우지 않는다. 필요하면 ‘앞에서 차로가 합쳐집니다’로 축약한다. 정확한 시점이 불확실하면 추가 음성을 내지 않는다. 지도만 보고 차량의 현재 차로를 확신하는 색 표시를 하지 않는다.

### S4. 통과·취소

구간을 지나면 조용히 기본 화면으로 돌아간다. 축하음이나 확인 버튼은 없다. 재경로·반대 방향·위치 신뢰 저하 시 카드를 취소한다.

### S5. 출발 전 예습·개발 패널

예습에서는 구간 전체 도식, 설명, 자료 기준일을 볼 수 있다. 개발 패널에서는 입력 출처, 후보 segmentId, 매칭 근거, 신뢰 단계, 안내가 억제된 이유를 확인한다. 이는 제품 주행 화면과 분리한다.

내장 내비 위 오버레이나 계기판 출력은 현재 확인되지 않았다. MVP는 독립 앱 화면을 기본으로 하고 실제 내비와 화면을 공유할 수 있는지 별도로 검증한다. 지원하지 않는 창 형태를 시안만으로 구현 완료처럼 제시하지 않는다.

## 9. 앱 내부 데이터 모델

아래는 제안 모델이며 SDK 클래스 이름이 아니다.

| 모델 | 필수 정보 |
|---|---|
| NavigationSnapshot | routeId?, location, heading?, receivedAt, sourceTimestamp?, tbtItems, source |
| RoadContextSegment | id, version, direction, corridorGeometry, centerline, approachStart, mergeStart, mergeEnd, laneConnectivity, explanationType |
| RoadEvidence | sourceUrl, sourceDatasetVersion, sourceCrs, checkedAt, reviewer, limitations, expiresAt, status |
| GuidanceTemplate | id, title, structuralText, conditionalText, diagramKey, voiceText?, requiredEvidence |
| MatchResult | segmentId?, confidenceLevel, longitudinalDistance?, reasons, rejectionReason? |
| GuidanceSession | routeGeneration, segmentId, state, lastAnnouncedAt, passId, userMuted |
| DecisionLog | timestamp, source, inputIds, ruleId, decision, suppressionReason, dataVersion |

confidenceLevel은 초기에는 HIGH/MEDIUM/LOW 규칙 기반 등급이다. 이를 통계적으로 보정된 확률이나 ‘안전 확률’로 표시하지 않는다. laneConnectivity는 구간 자체의 연결 관계이며 차량의 현재 차로 정보가 아니다.

Geometry는 원본 좌표계를 확인해 변환하고, 앱 저장·API 경계에서는 WGS84를 명시한다. 거리 계산 시 위도·경도 차이를 미터로 취급하지 않는다. topology의 단절·방향 역전·끝점 누락은 데이터 검증에서 차단한다.

## 10. 판정 엔진과 안내 상태 전이

`DISABLED → WAITING → CANDIDATE → PREVIEWED → APPROACHING → PASSED`

어느 상태에서든 경로 변경·오래된 입력·데이터 만료가 발생하면 `SUPPRESSED`로 전이한다. 입력이 회복되면 후보를 다시 평가하되 이미 통과한 안내를 즉시 반복하지 않는다.

초기 알고리즘:

1. 권한·SDK 연결·자료 승인 상태를 검사한다. 미승인 실제 구간은 후보에서 제외한다.
2. 위치를 해당 도로 corridor에 매칭한다. 인접한 고가·지하·평행 도로를 구별할 근거가 부족하면 LOW로 억제한다.
3. 최근 유효 위치의 진행 방향·이동 연속성으로 역방향을 배제한다. 정차 때 heading이 불안정하면 최근 유효 방향을 제한적으로 보존한다.
4. routeId와 TBT 순서를 보조로 확인한다. TBT 이름 하나만 일치하는 것은 HIGH의 근거가 아니다. routeId 자체도 도로 geometry를 제공하지 않는다.
5. 도로 중심선에 투영한 진행 거리로 예고 지점 도달을 판정한다. 유일한 경로 투영이 안 되면 숫자 거리와 자동 안내를 생략한다.
6. MVP 예고 초기값은 구조 변화 약 400m 전, 접근은 약 150m 전으로 두되 도로 속도와 구간 길이에 따라 검수 가능한 설정으로 저장한다. 이 값은 안전성이 검증된 기준이 아니다.
7. HIGH일 때 구조 설명 카드 1회. MEDIUM은 조건부 구조 정보만 예습 화면에서 제공하고 자동 음성은 금지. LOW는 안내 없음.
8. 합류 끝점을 지나 도로 진행 거리 100m 이상 벗어난 것을 확인하면 PASSED. 위치 점프만으로 통과를 확정하지 않는다.
9. 같은 passId에서는 한 번만 예고한다. 다시 실제 접근하는 경우에는 새 passId를 만들되 기본 5분 쿨다운을 적용한다.
10. 늦게 진입한 앱이 이미 합류 끝부분에 있다면 긴 예고는 생략한다. 과거 설명을 몰아서 재생하지 않는다.

위치는 새 콜백이 온다고 무조건 신선한 측정이 아니다. SDK가 원본 측정 시각을 주지 않으면 ‘수신 신선도’와 ‘이동 검증 상태’를 구별한다. 정차 때문에 좌표가 같을 수도 있으므로 같은 좌표라는 이유 하나만으로 GPS 고장을 확정하지 않는다. 현재 에뮬레이터에서는 독립적인 Android 위치 변경과 내비 오류 로그가 있어 정체 문제를 확인했다.

## 12. 권장 아키텍처와 저장 정책

`PleosNavigationSource / ReplayNavigationSource → SnapshotNormalizer → SegmentMatcher → StructureGuidanceEngine → GuidancePresenter`

- 입력·매칭·안내·화면을 분리한다. 동일 fixture로 엔진의 결정을 반복 재현할 수 있어야 한다.
- 실제 SDK 어댑터는 현재 Probe에서 검증한 API 호출부터 사용한다. listener 수명·중복 요청·실패 재시도는 제품에 맞게 정리한다.
- 도식은 검수된 topology를 바탕으로 자체 벡터로 그린다. 지도 스크린샷을 앱 리소스로 복사하지 않는다.
- MVP 서버는 불필요하다. 도로 데이터·템플릿은 버전 JSON, 로컬 설정은 가벼운 저장소에 보관한다.
- UI는 최신 상태만 표시한다. 비동기 응답은 routeGeneration과 연결해 이전 경로 응답이 새 안내를 덮지 않게 한다. SDK 응답에 세대 구분 정보가 부족하면 전환 중 안내를 억제한다.
- 경로·위치 로그는 개발 모드에서만 명시적으로 활성화한다. 기본 제품은 이동 경로를 장기 저장하거나 서버로 올리지 않는다.
- 사용자 신고는 주행 후 받는다. 정확한 위치를 첨부할 때는 사용자가 확인할 수 있어야 한다.

## 13. 개발 순서와 중단·축소 기준

### 단계 A: 검증 기반 인수

기존 Probe를 실행해 TBT 수신과 GPS 정체를 재현한다. 이미지·에뮬레이터·NaviHelper 버전을 기록한다. 공식 이미지/도구 조합과 입력 경로를 조사하고 해결 전후 로그를 남긴다. 콜백 값을 직접 바꿔서 SDK 성공으로 보고하지 않는다.

### 단계 B: 도로 데이터 기술 검증

검증 가능한 실제 구간 하나에서 진입 차로 지속·합류 끝점·진행 방향을 확보한다. 데이터가 없으면 가상 도로로 엔진 구현만 진행한다. **차로 구조 자료를 확보하지 못하면 실제 도로 안내 서비스의 핵심이 미완성**이다. TBT 목록만으로 완료 처리하지 않는다.

### 단계 C: 판정 엔진·UI

실제 도로와 무관한 fixture로 정상 접근·반대 방향·평행 도로·늦은 입력·재경로를 테스트한다. 독립 앱 화면, 조건부 문구, 도식, 반복 억제부터 구현한다.

### 단계 D: 통합 검증

이동 가능한 SDK 입력과 승인된 실제 구간을 함께 연결한다. 실제 지도·차량 위치가 맞아야 실시간 통합 완료다. 음성은 카드 동작이 안정된 뒤 추가한다.

### 단계 E: 시연과 인계

시연 데이터인지 실시간 데이터인지 화면·영상·설명에 일치하게 표시한다. 확인된 기능, 미확인 기능, 실패 사례를 함께 전달한다. 제출 규정·마감 시각은 별도로 확인한다.

시간이 부족할 때 줄일 것: 음성, 지역 확대, 전체 지도, 신고 기능. 줄이면 안 되는 것: 입력 출처 표시, 구조 데이터 근거, 현재 차로 미확인 처리, 재경로 취소, 오안내 억제.

단위 테스트는 매칭·상태 전이·쿨다운·경로 세대 폐기처럼 오안내를 막는 로직에 집중한다. 스크린샷이 보인다는 것만으로 안내 판단 성공을 판정하지 않는다.

완료 수준을 세 단계로 보고한다.

- **제품 시연 완료:** 명시된 시연 입력으로 UI·규칙·실패 처리가 작동.
- **SDK 통합 완료:** 실제 이동하는 SDK 입력으로 단계 전환을 확인.
- **실제 구간 검증 완료:** 최신 근거가 있는 실제 도로에서 구조·방향·타이밍을 검증.

세 수준을 하나의 ‘구현 완료’로 합치지 않는다. 실제 운전자 검증은 우선 정차 상태의 영상·도식 이해 테스트로 진행한다. 주행 평가가 필요하면 운전자에게 앱 조작을 맡기지 않고 동승 관찰 방식으로 계획한다.

UX 목표: 5명 이상의 초행 운전자에게 기존 안내와 구조 카드를 보여주고, ‘차로가 어디까지 이어지는지’를 정확히 설명하는 비율, 읽는 시간, 잘못 이해한 행동을 기록한다. 3초 내 이해·불필요한 조작 0회를 목표로 하되 현재 성과처럼 쓰지 않는다.

- 분석기: `scripts/summarize_callbacks.py`

분석기의 `merge_then_exit_same_callback_count`는 특정 진입 enum 뒤에 진출 enum이 있었다는 의미다. 실제 차로 합류 geometry를 검증했다는 의미가 아니다. `scripts/send_gps.py`는 입력 실험 도구이며 NaviHelper 위치 갱신을 해결한 도구가 아니다.

에뮬레이터는 한 인스턴스를 공유하므로 두 세션에서 동시에 경로 요청·위치 주입을 하지 않는다. 빌드·순수 로직 개발은 별도 프로젝트에서 진행하고, 실제 SDK 시험 시간은 작업 간 조율한다. 미결정 사항은 실제 시험 구간, 차로 자료 공급, 위치 갱신 해결책, 주행 중 화면 표시 방식이다. 각 사항은 증거가 확보될 때만 완료 상태로 바꾼다.

개발 완료 인계물은 독립 프로젝트 소스, 설치 가능한 APK, 빌드·실행 명령, 버전이 있는 구간 데이터와 근거, 가상·실제 입력 fixture를 구분한 파일, R01~R12 테스트 결과, 시연 영상 또는 화면 캡처, 미해결 항목이다. 도로 데이터의 출처와 검수 기록 없이 도식 화면만 전달하지 않는다.

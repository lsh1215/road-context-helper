# 초행길 — 성공 기준 기반 개발 실행 계획

작성: 2026-11-14 / 상태: 계획 수립 완료, 구현·새로운 실행 검증 전

## 1. 이번 작업의 계약

사용자가 요청한 최종 작업은 초기세팅부터 구현, 의도 검증, 실패 원인 수정과 재검증까지다. 이번 문서는 그 작업을 실행할 기준을 먼저 고정한다. 이 문서를 작성했다는 사실이나 화면이 렌더링된다는 사실을 앱 개발 완료로 보고하지 않는다.

제품 정의는 [기존 제품 계획서](./road-context-helper-plan.md)를 따른다. 목표는 **초행 운전자가 진입 차로의 지속·종료·합류 구조를 미리 이해하게 하는 것**이다. 교통량을 보고 끼어들 틈을 판단하거나 현재 차로를 알아내는 앱으로 바꾸지 않는다.

실행 경로는 초기세팅 스킬에 따라 `apps/road-context-helper/`로 확정한다. 기존 문서의 `products/road-context-helper/` 제안은 대체한다. 루트 Probe와 여행 사운드트랙 앱은 보존한다.

‘완벽하게’의 실행상 의미는 **사전에 정한 필수 성공 기준에 실패·미검증이 없고, 결과를 재현할 증거가 있으며, 미해결 결함을 숨기지 않는 상태**다. 모든 도로·모든 실제 차량에서 안전을 보증하는 의미로 사용하지 않는다. 외부 자료·사람의 평가·SDK 결함에 막히면 완료로 포장하거나 기준을 낮추지 않고 차단된 기준을 남긴다.

## 2. 현재 증거와 먼저 해결할 위험

| 사실 | 기존 증거 | 다음 확인 |
|---|---|---|
| NaviHelper 연결·TBT 수신 성공 | 루트 `test-results/callbacks.jsonl`, `summary.json` | 새 앱 어댑터에서도 재현 |
| 10개 TBT 안에 진입·진출 포함 | 같은 원본 로그 | 실제 합류 차로 geometry는 별도 확보 |
| 위치 50건, 좌표 1개 | `summary.json` | 실제 위치 갱신 성공과 구분 |
| Android 위치만 용산역으로 이동 | `location-system-final.txt` | 내비 위치와 일치 여부 |
| 내비가 NMEA 체크섬 오류 기록 | `gps-parser.log` | 공식 입력 경로·버전 조합으로 해결 검증 |
| 사용자 구간 정확한 위치 미확정 | 용산역→월곡역이라는 설명 | 임의로 IC 확정 금지 |
| 실제 차로 구조 자료 미확보 | 기존 제품 계획 | 승인 가능한 실제 구간 최소 1개 확보 |

핵심 위험은 UI 개발보다 먼저 조사한다. SDK 위치가 안 움직이고 도로 자료가 없는 상태에서 화면만 정교하게 만든 것을 실시간 제품 완료로 인정하지 않는다.

## 4. 완료 수준과 필수 게이트

| 수준 | 의미 | 필수 게이트 |
|---|---|---|
| L1 재현 가능한 제품 시연 | 가상 입력으로 핵심 경험·반례가 동작 | G0, G1, G2, G3, G5, G6 |
| L2 실제 SDK 통합 | 실제 SDK 위치·경로와 승인된 실제 구조 자료로 동작 | L1 + G4 |
| L3 사용자 가치 검증 | 초행 사용자가 짧은 노출로 구조를 이해 | L2 + G7 |

이번 제품의 전체 성공 목표는 **L3**다. 사람 평가가 아직 없으면 L2이며, 위치 문제가 남으면 L1 이하이다. 실차 시험은 별도 범위이며 에뮬레이터 통합을 실차 검증이라고 부르지 않는다. 시연용 가상 도로는 실제 구간 검증을 대체하지 못한다.

| 게이트 | 성공 기준 | 검사·산출물 |
|---|---|---|
| G0 범위·계약 | 핵심 문구, 입력 계약, 시연/실제 구분, 기준 ID 고정 | ADR, acceptance matrix, 스키마 |
| G1 초기세팅 | 독립 프로젝트 clean build·APK 설치·기동 성공, 최소 권한, Probe 보존 | 빌드 로그·APK 해시·manifest 점검 |
| G2 도로·로직 | 양성/음성/경계 시나리오 모두 기대 결과, 데이터 검증 통과 | 고정 fixture·단위 테스트·결정 로그 |
| G3 UX·화면 | 필수 상태와 창 크기에서 잘림·겹침 없음, 주행 조작 0회, 입력 출처 명확 | 실제 Android 스크린샷·UI 테스트·체크리스트 |
| G4 실시간 통합 | 실제 위치 변화·경로 일관성·구간 구조 근거·접근/통과 연결 성공 | SDK 원본·입력 trace·화면 시각 매핑 |
| G5 신뢰성 | 수명·오류·반복 실행에서 crash/ANR·중복 listener·중복 안내 없음 | 내구 시험·수명 계측·logcat |
| G6 독립 재현 | 고정 산출물로 별도 검토자가 동일 결과, 필수 결함 0 | 검증 명령·기준별 결과·독립 리뷰 |
| G7 사용자 이해 | 실제 사람의 2초 노출 이해 검사 기준 충족 | 익명 응답 원본·채점표·수정 이력 |

## 5. 성공 기준 상세: 기능과 오안내 억제

모든 기준의 상태는 `NOT_RUN / PASS / FAIL / BLOCKED` 중 하나다. 부분 성공은 PASS가 아니다. 각 결과에는 코드 식별자, 데이터 버전, fixture 해시, 명령, 기기 정보, 증거 경로를 연결한다.

| ID | 입력·조건 | 반드시 관측할 결과 |
|---|---|---|
| AC-01 | 승인된 구간, 올바른 방향, 신선한 위치로 예고점 통과 | 예고 카드 정확히 1회; 정상 입력을 모두 억제하는 구현은 실패 |
| AC-02 | 같은 공간의 반대 방향 | 자동 안내 0회 |
| AC-03 | 고가/지하/평행 도로 후보가 복수 | 임의 선택 없이 억제, 이유 기록 |
| AC-04 | 현재 차로 정보 없음 | 도로 구조 설명만; 현재 차로 아이콘·유지/변경 명령 없음 |
| AC-05 | 오래된 입력·좌표 점프·순서 역전 | 새 행동성 안내 없음; 마지막 신뢰 상태와 폐기 이유 기록 |
| AC-06 | 같은 콜백 100회 반복 | 안내 횟수 증가 0, 수신 건수와 이동 건수 구분 |
| AC-07 | 예고 뒤 경로 변경, 이전 응답 지연 도착 | 이전 카드·예약 작업 취소; 세대가 다른 입력 폐기 |
| AC-08 | 합류 끝부분에서 앱 시작 | 이미 지난 예고를 뒤늦게 출력하지 않음 |
| AC-09 | 자료 만료·검수 누락·구조 미지원 | 해당 구간 자동 안내 0; ‘위험 없음’ 표현 금지 |
| AC-10 | 좌표계 오류·끝점 누락·역방향 topology | 로딩 단계에서 거부, 앱 자체 crash 없음 |
| AC-11 | 통과 후 동일 구간 재접근 | 통과 확인과 쿨다운 충족 시 새 pass에서 1회만 안내 |
| AC-12 | 데이터 없음·권한 거부·SDK 미지원 | 미연결 상태, 실제 데이터인 듯한 기본 좌표/샘플 없음 |
| AC-13 | 모드 전환 또는 재시작 | 시연 상태 초기화, 실제/시연 데이터 혼합 0건 |
| AC-14 | SDK 연결 해제·재연결 | 새 유효 스냅샷 전 안내 없음, listener 중복 0 |
| AC-15 | 거리 의미 미확인 TBT | 숫자 감산·누적으로 합류 거리 생성 안 함 |
| AC-16 | NaN/범위 밖 좌표·null heading·없는 routeId | 명시적 유효성 처리, 추정값을 실측값으로 표시하지 않음 |
| AC-17 | 가상 clock의 400/150/100m 및 10초/5분 임계값 직전·동일·직후 | 경계별 예상 상태 일치, 무작위 시스템 시간 의존 없음 |
| AC-18 | 도로 자료 버전 변경·구간 비활성화 | 열려 있던 이전 자료의 카드 폐기, 이전 결정 재사용 금지 |

초기 거리·시간 값은 기존 계획의 실험값이다. 수치는 설정 파일에 버전으로 저장하고 양성 기준을 통과시키려고 임의로 변경하지 않는다. 변경 시 설계 이유와 새 평가가 필요하다.

## 6. 실시간 위치·데이터 게이트의 구체적 증거

### AC-19: 위치 갱신

일정 간격으로 연속된 위치 trace를 공식 지원 입력 경로에 전달한다. 20개 이상의 서로 다른 위치를 60초 이상에 걸쳐 입력하고 SDK에서 최소 10개의 방향·순서가 일관된 서로 다른 유효 위치를 수신한다. 새 콜백만 세거나 앱 내부 좌표를 바꿔 통과시키지 않는다. 수신 좌표와 입력 좌표의 차이·지연 분포를 기록한다. 좌표가 다르다는 사실만으로 도로 매칭 정확도까지 증명하지 않는다.

최초 기술 검증 예산은 시간 정렬된 좌표 오차 p95 20m 이하, 입력부터 SDK 수신까지 지연 p95 5초 이하로 고정한다. 이는 에뮬레이터 실험값이며 차로 판별 정확도 기준이 아니다. 시계 정렬 방법을 기록하고 정렬이 안 되면 지연 판정은 미검증이다. 오차 범위 안에 복수 도로가 있으면 이 수치가 통과해도 자동 안내를 억제한다. 실제 주행 속도에서 지연 동안 이동하는 거리를 계산해 예고 구간 안에 충분한 여유가 있는지도 AC-21에서 확인한다.

새로 확인한 공식 경로: [FusedLocation SDK 1.1.3 소개](https://document.pleos.ai/docs/pleos-only/connect-sdk-pleos/FusedLocation/intro)는 위치 업데이트 구독, 지원 여부 확인, 신뢰도·타임스탬프 필드를 안내한다. 이는 **현재 환경에서 테스트한 결과가 아니다**. 초기 기술 검증에서 `isSupported()`와 위치 구독을 확인할 가치가 있다.

후보 A는 NaviHelper 위치 갱신 원인 해결이다. 후보 B는 FusedLocation을 위치 소스로, NaviHelper를 경로 맥락 소스로 쓰는 명시적 결합이다. B를 사용하면 문서·로그·UI 진단에 소스를 기록하고 NaviHelper 위치 문제가 해결됐다고 보고하지 않는다. 두 소스의 시각·경로 일관성이 확인되지 않으면 결합 안내를 억제한다. Google Play Services 위치 API와 Pleos FusedLocation을 혼동하지 않는다.

### AC-20: 승인 가능한 실제 구간

최소 1개 실제 구간에 출처, 이용 조건, 좌표계, 제작/검수일, 방향, 진입 차로 지속 구간, 합류 끝점, 도식의 근거가 있어야 한다. 단순 TBT 이름·일반 지도 POI·AI 추정은 근거가 아니다. 다른 검토자가 원본과 도식을 대조한다. 사용자 사례의 위치를 특정하지 못하면 확인 가능한 다른 구간으로 평가하되 원래 구간 검증 상태는 미수행으로 둔다.

### AC-21: 위치에서 화면까지

AC-19와 AC-20을 연결해 접근→예고→통과를 실제 SDK 입력으로 3회 재현한다. 별도 정답 라벨과 실제 출력 시각을 비교한다. 각 통과에서 예고 1회, 통과 뒤 제거, 재경로 뒤 잘못된 잔존 0회가 필요하다. 순수 replay 통과는 이 기준을 통과시키지 않는다.

## 7. 사용 흐름과 화면 설계 작업

이 앱의 퍼널은 이용 시간을 늘리는 퍼널이 아니라 **사용 가능 확인→주행 대기→구조 이해→통과 후 자동 종료**다.

| 단계 | 사용자 질문 | 화면·행동 | 성공 신호 |
|---|---|---|---|
| 첫 실행 | 무엇을 알려주나? | 짧은 구조 예시, 권한이 필요한 시점의 설명 | 주행 시작까지 필수 조작 3회 이하 |
| 준비 | 지금 작동 가능한가? | 연결/자료 지원 여부, 필요하면 설정 진입 | 미지원과 정상 대기를 구별 |
| 대기 | 계속 봐야 하나? | 조용한 기본 화면 | 주행 중 필수 조작 0회 |
| 예고 | 이 진입로는 어떻게 이어지나? | 진행 방향 도식+핵심 1문장 | 2초 노출 후 구조 이해 |
| 접근 | 앞에서 무엇이 달라지나? | 같은 위치의 축약 정보 | 새로운 화면 탐색 불필요 |
| 통과 | 이제 끝났나? | 자동 해제 | 확인·닫기 조작 0회 |
| 실패 | 왜 안내가 없나? | 간단한 상태; 기술 상세는 정차/진단 화면 | 불확실성을 정상 작동으로 오인하지 않음 |

### 레이아웃 초안과 검토 순서

1. 실제 Pleos 앱 창의 가용 bounds·density·시스템 여백을 먼저 측정한다. 전체 2560×1440을 앱 캔버스로 가정하지 않는다.
2. 넓은 창: 상단 약 15% 상태/짧은 제목, 중앙 약 65% 도식과 핵심 문장, 하단 약 20% 간단한 제어. 비율은 초안이며 글자·터치 크기 기준보다 우선하지 않는다.
3. 좁은 창: 도식 위/문장 아래로 재배치하고 부가 정보를 생략한다. 중요한 구조를 잘라내거나 글자를 무작정 축소하지 않는다.
4. 도식은 진입 차로의 지속과 끝에서의 연결을 한 번에 보여준다. 실제 차량 아이콘·안전 녹색 화살표·차로 이동 명령처럼 보이는 애니메이션을 사용하지 않는다.
5. 강조색은 구조 설명에 한 가지, 중립 상태색은 별도로 둔다. 색만으로 방향·현재 상태를 전달하지 않는다.
6. 주행 화면에는 긴 설정·로그·좌표·점수·developer mode 버튼을 노출하지 않는다. 시연 모드 출처 표시는 예외로 계속 보인다.
7. 초기안 2개를 정적 도식으로 비교하고 한 안을 선택한 이유를 DESIGN.md에 남긴다. 이후 핵심 동작을 바꾸는 디자인 변경도 기준별로 재검증한다.

### AC-22~26: 화면 수용 기준

- AC-22: 실제 에뮬레이터의 지원 창 크기별, 밝은/어두운 테마, 글자 확대 상태에서 잘림·가림·버튼 중첩 0건. 지원하지 않는 창 형태는 구현했다고 주장하지 않는다.
- AC-23: 텍스트 대비 최소 4.5:1, 핵심 touch target은 프로젝트 목표 76×76dp 이상. Pleos의 물리 크기 기준은 에뮬레이터 px만으로 실차 준수라고 확정하지 않고 density·표시 크기 가정을 기록한다.
- AC-23 추가: 중요 글자 높이 5mm·보조 3mm라는 Pleos 기준을 설계에 반영하고, 표시 장치 크기가 미확정이면 물리 크기 적합은 미검증으로 남긴다. 핵심 조건을 작은 각주로 숨기지 않으며 문단은 최대 3줄, 자동 스크롤·주행 애니메이션은 사용하지 않는다.
- AC-24: 사용자 입력은 250ms 안에 상태 피드백. 처리 자체가 오래 걸리면 진행/대기 상태를 보이고 중복 제출을 막는다. 측정은 입력 이벤트와 UI 상태 갱신 timestamp로 수행한다.
- AC-25: 모든 카드·도식에서 주행 방향과 실제 차로 미확인 표현이 일치. 설명과 그림이 반대이면 중대 결함이다.
- AC-26: UI 자동 테스트로 대기/예고/접근/통과/오류/권한 거부/시연 상태를 확인하고 각 상태의 실제 Android 캡처를 저장한다. 웹 목업 캡처만으로 통과 금지.
- AC-26 추가: 정차/주행 상태별 플랫폼 표시 제한과 내장 내비 동시 사용 가능 형태를 실제 Pleos에서 확인한다. 주행 중 앱이 차단되면 핵심 사용 흐름은 실패다. 카테고리만 선언해 우회하지 않고 공식 지원 표시 방식으로 재설계·재검증한다.

## 8. 사용자 가치 평가: HEART의 Goal–Signal–Metric 적용

목표는 체류 시간·클릭 증가가 아니라 이해와 조작 감소다. 초기 제품에서 retention을 억지로 수집하지 않는다.

| 목표 | 관측 신호 | AC-27 사용자 평가 기준 |
|---|---|---|
| 구조 이해 | 도식을 본 뒤 차로가 어디서 합쳐지는지 설명 | 최소 5명, 균형 잡힌 4개 상황에서 전체 정답률 90% 이상·각 참가자 3/4 이상 |
| 빠른 인지 | 카드 2초 노출 뒤 정답 선택·설명 | 응답 시간과 정답을 별도로 기록; 장시간 읽기로 통과 금지 |
| 과신 방지 | ‘현재 차로를 아는가’, ‘지금 합류해도 되는가’에 대한 답 | 즉시 합류 허가·현재 차로 확정으로 해석한 응답 0건 |
| 부담 감소 | 기존 방향 안내 대비 이해도·주관 부담 | 대조 조건과 순서를 교차 배치, 결과 원문 기록 |

실제 사람에게 정차 상태에서 시행한다. 도로 전문가만 모집하지 말고 초행 운전 경험자가 포함되어야 한다. 동일 도식을 순서만 바꿔 반복 학습으로 점수를 높이지 않는다. 에이전트 역할극을 참가자 평가로 세지 않는다. 소표본 결과는 사용성 결함 발견용이며 사고 감소를 입증하지 않는다.

실패하면 문구·도식·타이밍 중 원인을 분리해 수정한 뒤 새 상황 또는 새로운 참가자로 재검증한다. 사람이 아직 참여하지 않았으면 G7은 BLOCKED 또는 NOT_RUN이며 완료로 표시하지 않는다. 독립 개발·자동 검증은 그동안 계속한다.

## 9. 초기세팅·기술 선택 계획

필수 스킬: [pleos-app-init](../.agents/skills/pleos-app-init/SKILL.md). 이 스킬은 초기세팅·빌드 골격까지 담당하며 이후 기능 구현은 사용자 요청과 본 계획을 따른다. 이번 단계는 계획 작성이며 아직 초기세팅 빌드를 수행한 것이 아니다.

- 경로: `apps/road-context-helper/`, applicationId: `dev.pleos.roadcontext`.
- 기존 Probe의 Java 코드는 보존한다. 새 독립 앱은 Kotlin + Jetpack Compose를 우선 검토한다. 단방향 상태·순수 엔진·UI 테스트에 적합하기 때문이다. Kotlin/Compose/AGP의 실제 호환 버전은 초기세팅 시 공식 표와 빌드로 확정한다.
- 설치된 Gradle 8.11.1, SDK 35, 기존 AGP 8.9.1과 NaviHelper 3.0.5를 재사용 후보로 둔다. 현재 설치 JDK와 Java target을 구분하고 불필요한 전역 변경을 하지 않는다.
- 공식 wrapper와 의존성 버전을 고정하고 앱 로컬 ignore·README·최소 manifest를 구성한다. 사용하지 않는 경로 변경·차량 제어 권한을 Probe에서 그대로 복사하지 않는다.
- 모듈 초안: `:app`(UI·생명주기), `:core`(순수 모델·엔진), `:data`(자료 검증·로드), `:integration`(Pleos 어댑터). 실제 규모가 작으면 패키지로 시작해도 경계와 소유권은 유지한다.
- 서버·계정·웹 앱·DB·공용 모노레포 도구는 기본으로 추가하지 않는다. 초기 번들은 JSON, 진단은 개발용 JSONL이다.
- 재경로 제어는 사용자 목적지가 아니므로 앱이 내비 목적지를 임의 변경하지 않는다. 연동 테스트의 경로 요청은 별도 Probe/시험 절차에서 수행한다.

## 10. 상태·인터페이스 계약을 먼저 고정

병렬 구현 전에 아래 계약을 core에 정의하고 버전을 붙인다.

- `NavigationSnapshot`: source, routeGeneration, routeId?, receivedMonotonicTime, measuredTime?, locationValidity, lat/lon?, heading?, TBT 목록.
- `RoadSegment`: 버전, 승인 상태, 방향, geometry, 연결 관계, 검수 근거·만료 시점. 실제 자료와 가상 fixture는 별도 namespace.
- `Decision`: 상태, 근거 segmentId, evidenceVersion, 이유 코드, 표시 문구 ID, diagramId, 거리 유효 여부.
- `Clock`: monotonic time과 wall time 분리. 단위 테스트는 가상 clock 사용.
- `NavigationSource`: 실제 SDK와 replay 구현. 모드 변경 시 세션 초기화, 한 세션 한 소스.
- 출처 enum은 `REAL_SDK / REPLAY_SYNTHETIC / REPLAY_CAPTURED`로 구분한다. 실제 SDK에서 녹화한 로그를 재생해도 실시간 입력은 아니다.
- `GuidanceState`: Waiting/Preview/Approaching/Suppressed/Passed/Unavailable. 기술 실패와 정상 대기를 구분.

매칭과 출력은 별도로 테스트한다. 내부 메서드를 그대로 흉내 낸 정답 생성기를 쓰지 않고, fixture별 기대 상태·안내 횟수·금지 문구를 수동 검수한 oracle로 저장한다.

추가 반례: routeId가 같아도 경로 변경 이벤트가 오는 경우, 위치와 TBT 시각이 다른 경우, 정차 중 heading 반전, wall clock 역행, 경계 양쪽을 반복하는 흔들림, 프로세스 복구 후 오래된 카드 재생. routeGeneration은 routeId 문자열만으로 결정하지 않는다.

에뮬레이터는 단일 소유 작업만 사용한다. 위치 주입·내비 목적지 변경·설치·종료를 병렬 실행하지 않는다. 순수 JVM 테스트와 문서 조사·UI 자산 작업은 병렬 가능하다. 검증자는 구현자와 다른 관점에서 실패 사례를 추가하고, 구현자가 자기 코드만 보고 통과 판정하지 않는다.

## 12. 단계별 실행과 반복 루프

1. **기준 잠금:** G0, AC 목록, 모델 계약, 판정 oracle, 변경 이력 양식을 만든다.
2. **초기세팅:** pleos-app-init 적용, 독립 앱 빌드·설치. G1 실패는 기능 개발 전에 수정한다.
3. **병렬 위험 해소:** SDK 위치, 실제 도로 자료, 화면 사용 가능성을 조사한다. 발견 결과를 설계와 성공 기준의 해석에 반영하되 실패를 없애려고 기준을 삭제하지 않는다.
4. **세로 기능:** replay 정상 접근 한 건을 입력→판정→도식→통과까지 연결한다. 이후 반례와 실제 입력을 추가한다.
5. **결정론 검증:** 양성/음성/경계 테스트를 실행하고 실패 fixture를 최소 재현으로 줄인다.
6. **실제 UI·SDK 검증:** 에뮬레이터에 APK 설치, 지원 창에서 상태별 캡처·입력·수명·로그 확인.
7. **독립 리뷰:** 기준별 증거를 읽고 실제로 재실행한다. 성공 주장과 로그가 불일치하면 실패로 되돌린다.
8. **개선:** 원인이 국소 오류면 수정, 상태·책임이 섞여 반복 실패하면 리팩토링. 관련 회귀 기준까지 재실행한다.
9. **사용자 이해 검증:** G7을 수행하고 문구·도식을 개선한다.
10. **최종 재현:** 고정 APK·데이터로 전체 필수 체크를 한 번 실행하고 결과를 인계한다.

각 루프는 `실패 기준 → 최소 재현 → 원인 가설 → 수정 → 대상 재검증 → 영향 범위 회귀 → 독립 판정`이다. 로그 없이 ‘아마 해결’로 종료하지 않는다. 같은 환경 오류를 재시도만 하지 말고 2회의 같은 실패 뒤에는 다음 시도 전에 다른 가설·관측 수단을 명시한다. 이는 작업 중단 횟수가 아니라 원인 분석 강제 규칙이다.

리팩토링 트리거 예: 같은 상태 결함이 다른 입력에서 반복됨, UI와 엔진의 판단 중복, SDK callback이 직접 화면 문구를 변경함, 이전 경로 취소를 여러 위치에서 제각각 처리함. 변경 전 실패 fixture를 보존하고 공개 계약이 바뀌면 모든 작업자에게 전달한다.

## 14. 증거·결함·기준 변경 관리

앱 아래에 다음 산출물을 만든다. 현재는 경로 계약이며 아직 생성된 테스트 결과가 아니다.

```text
apps/road-context-helper/
  README.md
  DESIGN.md
  docs/decisions/                 # 기술·데이터·UX 결정 이유
  verification/acceptance.json    # 기준, 상태, 증거 경로
  verification/scenarios/         # 수동 검수 정답과 입력
  verification/runs/<run-id>/     # 환경, 명령, 로그, 캡처, 요약
  verification/issues/           # 실패 기준·원인·수정·재검증
```

심각도는 S0 잘못된 구조/현재 차로 단정/실제 데이터 위장, S1 정상 안내 누락·경로 잔존·crash·필수 UI 불능, S2 이해 지연·비필수 시각 결함으로 구분한다. S0/S1 미해결 0건이 승격 조건이다. S2라도 AC 실패와 연결되면 해당 게이트는 통과하지 못한다.

기준 변경은 기존 값, 새 값, 이유, 영향, 추가 테스트를 기록한다. 기능이 어려워졌다는 이유만으로 필수 기준을 선택 기준으로 바꾸지 않는다. 제품 목적을 바꾸는 대안은 사용자에게 구체적 근거와 영향을 설명해야 한다. 일반적인 구현·수정·리팩토링은 이미 요청된 작업으로 진행한다.

## 15. 남은 외부 조건과 완료 보고 양식

외부 조건은 실제 구간 자료 접근·이용 조건, SDK 위치 입력의 정상 경로, 실제 사용자 평가 참여다. 로그인·자료 권한이 필요하면 독립 작업을 계속하며 필요한 부분만 요청한다. 공식 공모전 세부 공지는 이번 조사 도구에서 접근되지 않았으므로 스킬에 기록된 과거 확인을 최신 제출 조건으로 단정하지 않는다.

최종 인계에는 아래 항목이 모두 들어가야 한다.

1. 제품 동작과 설치 APK·소스 경로.
2. G0~G7 및 AC-01~30의 PASS/FAIL/BLOCKED/NOT_RUN 표.
3. 실제 SDK·실제 도로 자료·가상 시연 각각 무엇을 확인했는지.
4. 재현 명령, 버전·APK 해시·fixture 버전, 대표 캡처와 로그.
5. 발견된 결함과 리팩토링 내역, 최종 회귀 결과.
6. 사람 평가 결과와 남은 한계. 아직 없으면 미수행 표시.

‘빌드 성공’, ‘시연 성공’, ‘실시간 통합 성공’, ‘사용자 이해 확인’을 구분해서 보고한다. 모든 필수 게이트가 통과하기 전에는 전체 성공이라고 결론내리지 않는다.
